**Branch** `claude/calculation-error-check-ijdt9i` · **Commits** `72854b4`, `ba302e1`, `3de8201`
**สถานะ** ยังไม่ขึ้น production — อยู่ระหว่างตรวจสอบ

## สรุป

เจ้าหน้าที่ศูนย์ฯ สงขลาแจ้ง 2 อาการผ่าน LINE: (ก) ผลคำนวณโหมด "ผสมให้ได้" ไม่ตรงกับที่คำนวณมือ
และ (ข) แก้ปริมาณสารเคมี/ตัวทำละลายในหน้าแก้ไขสูตรแล้วค่าไม่เปลี่ยน ทั้งสองอาการมาจาก
**บั๊กคนละตัว** ที่บังเอิญอยู่ในโดเมนเดียวกัน และระหว่างตรวจพบบั๊กตัวที่สามซึ่งรุนแรงกว่าที่แจ้งมา
คือการกดบันทึกสูตรทำให้สัดส่วนเจือจางลง 1,000 เท่าทุกครั้ง

## บั๊กที่ 1 — โหมด "ผสมให้ได้" คิดตัวหารเกินไปหนึ่งส่วน

### อาการ

ฉลาก "สารเคมี 1 ลิตร ผสมน้ำมันให้ได้ 14 ลิตร" ฉีดพ่น 20 มล./100 ตร.ม. เตรียม 5 ลิตร

| ค่า | ระบบคำนวณได้ | ที่ถูกต้อง |
|---|---|---|
| สารเคมีต่อส่วนผสม 1 ลิตร | 66.67 มล. | **71.43 มล.** |
| เตรียม 5 ลิตร → สารเคมี | 333.33 มล. | **357.14 มล.** |

คลาดเคลื่อน 7% — ทุกสูตร "ผสมให้ได้" เจือจางเกินจริงหนึ่งส่วน

### สาเหตุเชิงโค้ด

`src/lib/calculations.ts` (ก่อน `72854b4`) ใช้สูตรเดียวกันทั้งสองโหมด:

```ts
} else {
    // แบบ 1 "ผสมให้ได้" (ปริมาตรรวมคงที่ = V_total_ref)
    V_total = V_total_ref;
    const fC = C / (C + S);   // ← ตีความ S เป็น "ตัวทำละลายล้วน"
```

`C / (C + S)` ถูกต้องก็ต่อเมื่อ `S` คือตัวทำละลายล้วน แต่ชื่อโหมดคือ "ผสมให้ได้ (ได้สุทธิ)"
ซึ่งบนฉลากหมายถึง **ยอดรวม** เจ้าหน้าที่จึงต้องลบเองก่อนกรอก (`14 - 1 = 13`)

โค้ดสอนกฎนี้ไว้จริงที่ `src/components/calculator/label-guide.tsx`:

> "ผสม 1 ลิตร กับน้ำให้ได้ 40 ลิตร 👉 C = 1, S = 39 (มาจาก 40-1)"

แต่ช่องกรอกเขียนว่า "ปริมาณตัวทำละลายที่ระบุข้างขวด" และ**ไม่มีใครลบ** ข้อมูลจริงในฐานข้อมูล
ยืนยันเรื่องนี้: ทุกสูตร "ผสมให้ได้" กรอกยอดรวมจากฉลากตรง ๆ

### ทำไมอาการจึงเป็นแบบนั้น

`fC` ต่างกันแค่ `1/15` กับ `1/14` จึงไม่ใช่ความผิดพลาดที่เห็นชัด ระบบทำงานปกติทุกอย่าง
ให้ตัวเลขที่ดูสมเหตุสมผล แต่เจือจางเกินจริงเสมอ ยิ่งอัตราส่วนเข้มข้น (S น้อย) ยิ่งคลาดมาก —
ที่ 1:14 คลาด 7% แต่ที่ 1:200 คลาดเพียง 0.5% จึงไม่มีใครสังเกตจนกระทั่งเจอสูตรเข้มข้น

### การแก้ (`72854b4`)

```ts
const fC = mix_type === 2 ? C / (C + S) : C / S;
```

`S` = ตัวเลขบนฉลากเสมอ ไม่ต้องคำนวณเอง พร้อมแก้ `label-guide` ที่สอนกฎเดิม, ทำให้หัวข้อ
ช่องกรอกเปลี่ยนตามโหมด, ปรับ `S` ของสูตรตั้งต้นใน `constants.ts`/`api/seed` เป็นยอดรวม
และ migration `20260817_fix_mix_type_1_total_volume.sql` สำหรับสูตรตั้งต้นในฐานข้อมูล

แถมแก้อีกจุดที่พบระหว่างทาง: `targetVolume` ในโหมด "ผสมกับ" ไม่ตรงกับป้าย "รวม X ลิตร"
เพราะคิดตัวทำละลายเต็ม 1,000 มล./ลิตร แล้วเติมสารเคมีทบ (1:4 ขอ 5 ลิตร ได้จริง 6.25 ลิตร)

## บั๊กที่ 2 — `C`/`S` ขัดแย้งกับหน่วยของตัวเอง

### อาการ

แก้ปริมาณสารเคมีและตัวทำละลายในหน้าแก้ไขสูตร กดบันทึก แล้วค่ากลับเป็นเหมือนเดิม

### สาเหตุเชิงโค้ด

`label_profiles` เก็บ `C`/`S` เป็น **สัดส่วนที่ย่อแล้วและไม่มีหน่วย** แต่เก็บ `C_unit`/`S_unit`
เป็น **หน่วยที่เจ้าหน้าที่พิมพ์ตอนกรอก** ข้อมูลสองส่วนนี้ขัดแย้งกันเอง

`src/components/admin/profiles-table.tsx` (ก่อน `ba302e1`) ย่อสัดส่วนก่อนบันทึกทุกครั้ง:

```ts
function normalizeCS(C: number, CUnit: 'L' | 'cc', S: number, SUnit: 'L' | 'cc') {
    const C_ml = CUnit === 'L' ? C * 1000 : C;
    const S_ml = SUnit === 'L' ? S * 1000 : S;
    return simplifyRatio(C_ml, S_ml);   // ← ย่อก่อนบันทึก
}
```

พิมพ์ `100 มล. : 25 ลิตร` → บันทึก `C=1, S=250` คู่กับหน่วย `cc`/`L` ซึ่งอ่านตรงตัวได้ว่า
**1:250,000** ตารางจึงแสดง "1 มล. / 250 ลิตร" ไม่ใช่สิ่งที่พิมพ์ และแก้เลขใหม่ก็ถูกย่อกลับ
เป็นสัดส่วนเดิม

`src/lib/validations.ts` ระบุโมเดลนี้ไว้ตรง ๆ ว่า `C_unit`/`S_unit` เป็น *"informational only,
never read by calculate()"* — ซึ่งเป็นจริงในตอนนั้น และนั่นคือสิ่งที่ปิดบังบั๊กไว้

### หลักฐานที่ยืนยันสาเหตุ

รายการสารเคมีที่เจ้าหน้าที่ติ๊กส่งมา **ตรงกับเงื่อนไขนี้ทั้ง 10 แถว**: แถวที่ติ๊กคือแถวที่ `C` กับ `S`
กรอกคนละหน่วย (มล. กับ ลิตร) ทั้งหมด ส่วนสองแถวที่ไม่ติ๊ก — `อะควา เค-โอทริน` (1 มล. : 40 มล.)
และ `ไดนาโฟส 10` (1 ลิตร : 100 ลิตร) — คือแถวที่หน่วยตรงกันและอยู่ในรูปย่อที่สุดอยู่แล้ว
จึงแสดงผลตรงกับที่พิมพ์และไม่มีอาการ

## บั๊กที่ 3 — สัดส่วนถูกทบ 1,000 เท่าทุกครั้งที่บันทึก (ไม่ได้ถูกแจ้ง พบระหว่างตรวจ)

### สาเหตุเชิงโค้ด

`openEditDialog` seed ฟอร์มด้วยหน่วยเดิมคู่กับตัวเลขที่ **ย่อไปแล้ว**:

```ts
setEditCUnit(profile.C_unit || 'L');   // 'cc'
setEditSUnit(profile.S_unit || 'L');   // 'L'
setEditData({ ..., C: profile.C, S: profile.S });   // 1, 250 (ย่อแล้ว)
```

กดบันทึกจึงได้ `normalizeCS(1, 'cc', 250, 'L')` = `simplifyRatio(1, 250000)` = `C=1, S=250000`

หน่วยถูกนำไปคูณกับตัวเลขที่ผ่านการแปลงหน่วยมาแล้วรอบหนึ่ง — **ทบขึ้นทุกครั้งที่บันทึกซ้ำ**
จำลองด้วยโค้ดเดิมเทียบโค้ดใหม่:

```
เดิม   1:250  →  1:250,000  →  1:250,000,000  →  1:250,000,000,000
ใหม่  100:25  →  100:25     →  100:25         →  100:25
```

อาการเดียวกันอยู่ที่ `public-formula-actions.tsx` (หน้าผู้ใช้ทั่วไป) และ
`bulk-edit-profiles-modal.tsx` (แก้หลายรายการพร้อมกัน) ด้วย

### ทำไมจึงร้ายแรงกว่าสองตัวแรก

บั๊กนี้ **ไม่มีอาการให้เห็น** ตัวเลขที่ได้ยังดูเป็นสัดส่วนปกติ (`1:250000` ก็ยังเป็นตัวเลขที่อ่านได้)
และเกิดจากการกดบันทึกโดยไม่ต้องแก้อะไรเลย ผลคือสารเคมีเจือจางจนไม่ออกฤทธิ์ โดยที่หน้าจอ
ไม่แสดงอะไรผิดปกติ

## การแก้ (`ba302e1`)

เปลี่ยนโมเดลการเก็บข้อมูล: `C`/`S` เก็บ **ตามที่พิมพ์** โดย `C_unit`/`S_unit` เป็นหน่วยจริง
ของตัวเลขนั้น และ**แปลงหน่วยตอนคำนวณเท่านั้น**

`src/lib/cs-units.ts` (ใหม่) เป็นจุดแปลงหน่วยจุดเดียว แทนโค้ดที่ซ้ำอยู่ 5 ที่:

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `normalizeCSForCalc()` | แปลงเป็นหน่วยเดียวกันก่อนเข้า `calculate()` |
| `csEditState()` | seed ฟอร์มแก้ไข โดยคงสภาพ "ไม่มีหน่วย" ไว้ |
| `csSavePayload()` | แปลงกลับเป็น payload — ไม่ย่อ ไม่แปลงหน่วย |
| `applyCSUnitChoice()` | สลับหน่วย โดยบังคับให้อีกข้างมีหน่วยตามไปด้วย |

กฎที่ตรึงบั๊กที่ 3 ไว้: **`csSavePayload(csEditState(p))` ต้องได้ค่าเท่าเดิมเป๊ะ** มีเทสต์คุม
รวมถึงการวนซ้ำ 5 รอบต้องนิ่ง

เหตุผลที่การแก้นี้ไม่กระทบผลคำนวณ: `calculate()` ขึ้นกับ **สัดส่วน** C:S ล้วน ๆ การเก็บ
`100:25` แทน `1:250` จึงให้ผลเท่ากันทุกประการ — มีเทสต์ scale-invariance คุมสมมติฐานนี้ไว้

จุดที่พลาดไม่ได้: `use-calculator-engine.ts` เดิม **ตัด `C_unit`/`S_unit` ทิ้ง** ตอน map
ข้อมูลจาก API (`formattedProfiles`) ถ้าแก้ฝั่งบันทึกโดยไม่แก้ฝั่งอ่านนี้ก่อน โหมด "ผสมกับ"
จะได้ `fC = 0.8` แทน `0.004` = **สารเคมีเข้มเกินจริง ~200 เท่าแบบเงียบ ๆ**

ป้องกันเพิ่มที่ชั้น API: `profileMutationSchema` เพิ่ม `superRefine` บังคับให้หน่วยมาเป็นคู่เสมอ
(มีข้างเดียวคือรูปร่างของบั๊กที่ 3 พอดี) กัน browser bundle เก่าที่ค้างอยู่ระหว่าง deploy

## หาเจอได้อย่างไร

บั๊กที่ 1 ตรงไปตรงมา — เอกสารที่เจ้าหน้าที่ส่งมามีทั้งโจทย์ ผลจากระบบ และผลที่คำนวณมือ

บั๊กที่ 2–3 ยากกว่า สมมติฐานที่ตั้งแล้ว **ถูกตัดทิ้ง**:

1. *สูตรที่มี `formula` JSONB ถูก stored value บัง* — ตัดทิ้ง: `runFormula()` ทางเดิน
   `tank-dilution` ไม่อ่าน `formula.inputs` เลย ส่ง `formValues` เข้า `calculate()` ตรง ๆ
2. *ผลลัพธ์ถูก memoize ด้วย dependency ที่ขาด C/S* — ตัดทิ้ง: ไม่มี `useMemo` ในเส้นทางนั้น
3. *มี `useEffect` เขียนทับค่าที่ผู้ใช้แก้* — ตัดทิ้ง: `handlePresetChange` ถูกเรียกจาก
   event เท่านั้น ไม่มี effect ที่ผูกกับ `selectedPreset`

สิ่งที่ชี้ตัวจริงคือ **การจับคู่รายการที่เจ้าหน้าที่ติ๊กกับสภาพหน่วยของแต่ละแถว** — ตรงกันทั้ง 10 แถว
โดยสองแถวที่ไม่ติ๊กคือสองแถวที่หน่วยตรงกันพอดี นั่นทำให้ชัดว่าตัวแปรคือ "หน่วยไม่ตรงกัน"
ไม่ใช่กลไกของ React หรือ formula engine

## ทำไมหลุดมาได้

- **บั๊กที่ 1 — ช่องว่างระหว่างโค้ดกับหน้างาน** โค้ดถูกต้องตามกฎที่ตัวเองประกาศไว้ (S = ตัวทำละลาย)
  และมีเทสต์ครบ แต่กฎนั้นต้องให้มนุษย์ลบเลขเองก่อนกรอก ซึ่งไม่เกิดขึ้นจริง เทสต์ที่มีอยู่
  ตรึง *สูตรคณิตศาสตร์* ไว้ แต่ไม่ได้ตรึง *ความหมายของ input ที่ผู้ใช้กรอกจริง*
- **บั๊กที่ 2–3 — ไม่มีเทสต์ระดับ round-trip** เทสต์เดิมคุม `simplifyRatio()` และ `calculate()`
  แยกกัน ซึ่งทั้งคู่ถูกต้อง บั๊กอยู่ที่ *รอยต่อ* ระหว่าง save กับ edit ที่ไม่มีเทสต์ครอบ
  และ repo ไม่มี component test harness (`vitest.config.ts` รับเฉพาะ `src/**/*.test.ts`)
  จึงเขียนเทสต์ครอบ dialog ตรง ๆ ไม่ได้ — การแก้จึงต้องดึงตรรกะออกมาเป็นโมดูล pure ก่อน
- **บั๊กที่ 3 ไม่มีอาการ** ไม่มีทางถูกรายงาน ต้องเจอจากการอ่านโค้ดเท่านั้น
